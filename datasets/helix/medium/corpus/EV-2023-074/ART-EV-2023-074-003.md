# API Storage Migration Discussion — 2023-07-10

**Attendees:** Daniel Kim, Mei Lin  
**Note-taker:** Mei Lin

## Agenda

- Review current API query performance
- Discuss potential storage migration options
- Outline migration strategy and timeline

## Discussion

- **Daniel:** “We’re hitting slowdowns on the `/orders` endpoint, especially with the join-heavy reports. Mongo’s flexible schema is great, but the queries are getting sluggish.”
- **Mei:** “I’ve been profiling the API layer; the bottleneck is definitely the database read latency. PostgreSQL would give us indexed joins and better caching.”
- **Daniel:** “What about the data model? We’d need to map the document fields to relational tables.”
- **Mei:** “I’ve drafted a rough ER diagram. It’s a bit of work, but the schema is straightforward. We can keep the JSON columns for semi-structured data if needed.”
- **Daniel:** “If we go ahead, we should do it in phases to avoid downtime. Maybe start with the read‑only reporting tables first.”
- **Mei:** “Agreed. I’ll set up a migration pipeline in GitLab CI. Pipeline updated to include a data sync job and a rollback plan.”
- **Daniel:** “Let me know if you spot issues with the schema. I’ll coordinate with the devs to lock the API changes for the sprint.”

## Decisions

- **Migration to PostgreSQL**: agreed as the best path forward for faster query performance and tighter integration with existing operational tooling.
- **Phased approach**: start with read‑only reporting tables, then move core API data in the next sprint.
