# Postmortem: Load Balancer Misconfiguration Outage — 2023-07-24

**Incident date:** 2023-07-20  
**Severity:** SEV-2  
**Authors:** Victor Chen (Security Analyst), Ethan Brooks (DevOps Engineer)  
**Status:** Draft

## Summary

On July 20th, a misconfigured load balancer caused a 30‑minute API outage for our production cluster. Traffic was inadvertently dropped, impacting all external API consumers. The incident was detected by automated monitoring, escalated to the DevOps team, and resolved by rolling back the load balancer to its previous stable configuration and re‑applying the correct routing rules. Post‑incident, we added a health‑check probe and updated alerting to notify the DevOps team within seconds of any future misconfiguration.

## Timeline

- **08:12** – Monitoring alerts triggered: “HTTP 503 – No upstream available”  
- **08:13** – Incident opened in Jira; DevOps team notified via Slack  
- **08:15** – Ethan identified misconfigured load balancer rules in the Terraform state  
- **08:18** – Rollback of load balancer to previous stable configuration executed  
- **08:20** – Re‑applied correct routing rules and verified connectivity  
- **08:22** – Health‑check probe added to the load balancer configuration  
- **08:25** – Alerting rules updated to trigger within seconds on misconfiguration  
- **08:30** – All endpoints confirmed operational; incident closed in Jira  

## Root cause

The root cause was a misconfiguration in the load balancer’s routing rules. An accidental change in the Terraform script caused the load balancer to drop all traffic destined for the production cluster. Because the load balancer lacked a health‑check probe, the misconfiguration went unnoticed until external monitoring detected the 503 errors. The absence of immediate alerting for misconfigurations delayed detection and response.

## Contributing factors

- No health‑check probe on the load balancer to detect routing issues early  
- Alerting rules were not configured to notify the DevOps team within seconds of a misconfiguration  
- The Terraform change was not reviewed by a second engineer before deployment  

## What went well

- Rapid detection through automated monitoring  
- Quick escalation and clear communication via Slack and Jira  
- Effective rollback and re‑application of correct routing rules  

## What went poorly

- Lack of health‑check probe delayed detection of the routing issue  
- Alerting was not timely enough to prevent the 30‑minute outage  
- The Terraform change lacked a peer review process

## Lessons learned

This incident highlighted the critical need for health‑check probes on load balancers and real‑time alerting for configuration changes. By implementing these safeguards, we can detect and remediate similar issues before they impact customers.
