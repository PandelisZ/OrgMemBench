# Incident: Load Balancer Misconfiguration — INC-2023-02-03-01

**Status:** Identified  
**Severity:** SEV-2  
**Started:** 2023-02-03 09:12  
**Resolved:** 2023-02-03 09:45  
**Customer impact:** Service interruptions for a subset of mid‑market freight‑forwarding clients; API latency spiked and some requests failed.  
**Incident commander:** Ethan Brooks

## Current understanding

The load balancer was routing traffic to an unhealthy instance because the health‑check flag was missing from its configuration. This caused a cascade of failed requests across the platform. We have identified the misconfiguration and rolled back to the previous stable state.

## Timeline (live‑updated)

- 09:12 — First alerts from CloudWatch: “Instance unhealthy” on LB1.  
- 09:15 — Ops team notified via Slack; initial investigation begins.  
- 09:20 — Ethan and Daniel Kim confirm LB1 missing `--health-check` flag.  
- 09:25 — Rollback to previous LB config executed.  
- 09:30 — Health‑check script deployed to all instances.  
- 09:35 — New alerting rule added: notify Ops within 5 min of similar failure.  
- 09:45 — Traffic stabilizes; metrics return to baseline.

## Mitigation

- Rolled back to the last known good LB configuration.  
- Applied corrected settings with the required health‑check flag.  
- Deployed an automated health‑check script to all instances.  
- Added a new alerting rule to catch future misconfigurations within 5 minutes.

## Customer comms

- 09:20 — Service status page updated: “Partial outage due to load balancer issue.”  
- 09:30 — Email sent to affected clients: “We’re working on the issue; updates will follow.”

On resolution (09:45). Deploying now; let me know if you spot any issues. Thanks for the support.
