# Postmortem: Misconfigured Load Balancer Outage — 2023-02-10

**Incident date:** 2023-02-03  
**Severity:** SEV-2  
**Authors:** Daniel Kim, Ethan Brooks  
**Status:** Final  

## Summary  
On February 3rd, a misconfigured load balancer caused traffic to be routed to an unhealthy instance, resulting in a brief service outage for several mid‑market freight‑forwarding customers. The outage lasted approximately 30 minutes and impacted API availability. The Ops team was notified within minutes of the failure, and the incident was resolved by rolling back to the previous stable configuration, applying the corrected settings, and deploying an automated health‑check script.

## Timeline  

- **09:00** — Load balancer health‑check flag missing; traffic routed to unhealthy instance.  
- **09:05** — Ops team alerted via existing monitoring; incident opened in Jira.  
- **09:10** — Ethan Brooks identifies misconfiguration in load balancer settings.  
- **09:15** — Rollback to previous stable configuration performed.  
- **09:20** — Corrected load balancer settings applied.  
- **09:25** — Automated health‑check script deployed to monitor instance health.  
- **09:30** — New alerting rule added to notify Ops within 5 minutes of similar failure.  
- **09:35** — Service restored; API availability confirmed.  
- **09:40** — Incident closed in Jira; postmortem drafted.  

## Root cause  
The root cause was a missing health‑check flag in the load balancer configuration. Without this flag, the load balancer could not detect that the instance was unhealthy and continued to route traffic to it, leading to the outage. The absence of an automated health‑check script and an alerting rule further delayed detection and response.

## Contributing factors  

- Lack of automated health‑check script prior to the incident.  
- No alerting rule for load balancer health‑check failures.  
- Insufficient documentation of load balancer configuration requirements.  

## What went well  

- Rapid identification of the misconfiguration by Ethan Brooks.  
- Swift rollback to a known good configuration.  
- Deployment of an automated health‑check script and alerting rule within the same incident window.  

## What went poorly  

- Initial absence of a health‑check flag caused traffic to be routed to an unhealthy instance.  
- No pre‑incident monitoring or alerting for load balancer health‑check failures.

## Lessons learned  
This incident highlighted the critical importance of enforcing health‑check flags on load balancers and maintaining automated health‑check scripts. Proactive monitoring and alerting are essential to detect and remediate such misconfigurations before they impact customers.
