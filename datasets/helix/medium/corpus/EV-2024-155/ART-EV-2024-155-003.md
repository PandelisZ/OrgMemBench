# Postmortem: Retrospective Correction of 2023‑10‑12 API Outage Root Cause — 2024‑05‑20

**Incident date:** 2024‑05‑20  
**Severity:** SEV‑1 (high impact to internal reporting)  
**Authors:** Rajesh Kumar (P‑0005), Maya Patel (P‑0001)  
**Status:** Final  

## Summary  
On 2024‑05‑20 we amended the incident report for the 2023‑10‑12 API outage to correct the root‑cause attribution. Previously we believed a mis‑configured load balancer caused the outage; we now understand that a database schema change introduced a breaking change that was not caught by automated tests. The correction was approved by Maya Patel and Rajesh Kumar and updated across all internal documentation.

## Timeline  

- **09:00** – Maya Patel identifies a discrepancy between the 2023‑10‑12 post‑mortem and recent audit logs.  
- **09:15** – Rajesh Kumar pulls the database migration history and discovers a schema change applied on 2023‑10‑10 that removed a required column.  
- **09:30** – Investigation reveals the change was not covered by automated tests and caused the API outage.  
- **10:00** – Rajesh drafts a correction note and shares it with the incident response team.  
- **10:15** – Team reviews the evidence; consensus that the load balancer was not the root cause.  
- **10:30** – Maya Patel and Rajesh Kumar approve the correction.  
- **10:45** – Incident report for 2023‑10‑12 is updated in Confluence and the internal wiki.  
- **11:00** – Updated documentation is communicated to all stakeholders via Slack.  

## Root cause  
The root cause of the 2023‑10‑12 API outage was a database schema change that removed a column required by the API layer. The change was introduced on 2023‑10‑10 and deployed without automated regression tests covering the affected schema. Consequently, the API layer attempted to read the missing column, leading to a cascade of failures that lasted approximately three hours.

## Contributing factors  

- Lack of automated tests for database schema migrations.  
- No pre‑deployment validation step for schema changes.  
- Insufficient documentation of schema evolution in the incident response playbooks.  

## What went well  

- Rapid identification of the discrepancy by Maya Patel.  
- Clear evidence gathering and consensus building before approving the correction.  
- Transparent communication of the updated root cause to all stakeholders.  

## What went poorly  

- Initial misattribution to a load balancer mis‑configuration, which delayed the correct diagnosis.  
- Absence of automated checks for schema changes allowed the breaking change to go unnoticed.  

## Action items  

- [ ] @Rajesh Kumar: Implement automated schema migration tests in the CI pipeline — by 2024‑06‑15 [P1]  
- [ ] @Maya Patel: Update the incident response playbook to include a schema change validation step — by 2024‑06‑01 [P1]  
- [ ] @Engineering Lead: Conduct a quarterly review of all database migrations for test coverage gaps — by 2024‑07‑01 [P2]  

## Lessons learned  
This correction underscores the importance of rigorous testing for database schema changes. By embedding schema validation into our CI/CD process and updating our incident response playbooks, we can prevent similar misattributions and ensure faster, more accurate root‑cause analysis in the future.
