# Postmortem: 2021-05-22 Service Outage — Corrected Root Cause Analysis

**Incident ID:** INC-2021-05-22-001 (revision 2)  
**Postmortem date:** 2022-06-15  
**Severity:** SEV-2  
**Authors:** Arjun Mehta (Engineering Lead), Luis Hernandez (Operations)  
**Status:** Final — supersedes the preliminary incident summary filed 2021-05-22  

---

## Background

When the 2021-05-22 outage was first resolved, the team's working theory was a load balancer misconfiguration introduced during that afternoon's deployment. Omar Khaled and Omar Farah confirmed missing health-check configuration on the LB, Arjun Mehta rolled back the deployment, and the service recovered. That understanding was documented in the incident Slack thread and in the initial incident report, and no further investigation was carried out at the time.

In early June 2022, a routine review of infrastructure change logs surfaced an anomaly: the load balancer configuration snapshot from 2021-05-22 showed valid health-check settings both immediately before and after the deployment window. This discrepancy prompted a deeper investigation, the findings of which are documented here.

---

## Corrected Root Cause

The actual root cause of the 2021-05-22 outage was a misconfigured DNS record, not a load balancer misconfiguration.

The DNS A-record for `api.helix-internal.example` was updated on 2021-05-21 as part of an infrastructure provisioning task. The update pointed the record to a staging instance that had been decommissioned two days earlier. When the deployment on 2021-05-22 triggered a fresh service-discovery lookup, all inbound API traffic was routed to the dead IP. From the application layer this was indistinguishable from an unhealthy load balancer, which explains why the on-call team's first-pass diagnosis pointed to the LB.

The rollback that resolved the incident worked not because it corrected the load balancer, but because it forced a restart of the service-discovery process, which — after the restart — fell back to a cached pre-update DNS entry still pointing at the live instance. The actual DNS record was not corrected until 2022-06-15 during the course of this investigation.

**The load balancer misconfiguration hypothesis is ruled out.** Archive logs, config snapshots, and DNS query logs reviewed during this investigation are consistent in showing that the LB health-check was correctly configured throughout the incident window.

---

## Evidence Reviewed

- DNS change log entry 2021-05-21 18:42 UTC: A-record `api.helix-internal.example` updated (author: automated provisioning script `infra-provision-v0.9.2`).
- DNS resolver logs 2021-05-22 14:00–16:10 UTC: sustained NXDOMAIN / connection-refused responses for the target IP.
- Load balancer configuration snapshots at T-1h, T+0, T+30m, T+2h: health-check configuration unchanged across all four snapshots.
- Service-discovery restart event 2021-05-22 14:10 UTC: correlates exactly with the recovery window logged in the original incident report.
- No deployment diff affecting LB config was present in the 2021-05-22 release package.

## Timeline (Revised)

- **2021-05-21 18:42** — Automated provisioning script updates DNS A-record to a decommissioned staging IP.
- **2021-05-22 14:00** — Service degradation detected; 503 errors across API endpoints. On-call paged.
- **2021-05-22 14:05** — Omar Khaled and Omar Farah observe LB health-check failures in the dashboard and attribute the outage to LB misconfiguration. (This diagnosis, while understandable given the available signals, is now known to be incorrect.)
- **2021-05-22 14:10** — Arjun Mehta initiates deployment rollback. Service-discovery restart triggers fallback to cached DNS entry pointing at the live instance.
- **2021-05-22 14:30** — Health checks pass; traffic restored. LB settings restored to prior config as a precaution (this action had no effect on root cause).
- **2021-05-22 16:00** — Incident marked resolved. Postmortem scheduled. Root cause recorded as LB misconfiguration.
- **2022-06-01** — Routine infrastructure audit surfaces discrepancy in LB config snapshots.
- **2022-06-08** — DNS change log reviewed; decommissioned-IP record identified.
- **2022-06-15** — DNS A-record corrected. Postmortem completed. Root cause revised.

---

## Contributing Factors

- The automated provisioning script `infra-provision-v0.9.2` did not verify that target IPs were live before updating DNS records.
- No DNS health-check existed in the deployment pipeline; the monitoring stack only checked LB and application-layer endpoints.
- Service-discovery cache TTL masked the DNS error during normal operation, making the failure non-obvious until a fresh lookup was forced.
- The initial incident timeline made LB misconfiguration a plausible first explanation, and with service restored quickly there was no forcing function to revisit the diagnosis.

## Lessons Learned

The 2021-05-22 incident illustrates how a plausible first hypothesis, combined with a quick recovery, can foreclose further investigation. The team's rollback worked — service came back up — and the pressure to close the incident in a two-hour window meant the underlying DNS issue remained undetected for over a year.

Two process changes follow from this. First, incident postmortems should include a mandatory cross-check of DNS and network-layer logs, not only application and LB logs. Second, when a service-discovery restart is the mechanism of recovery, that fact should prompt a DNS investigation before the incident is closed: recovery via restart is often masking a stale record rather than confirming the hypothesis that preceded the restart.
